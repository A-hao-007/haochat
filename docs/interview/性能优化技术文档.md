## 二、整体架构：一条消息的完整生命周期 ⭐

这是整个面试的"地基"。不管面试官问什么，先把这条链路讲清楚，后面所有优化点都挂在这条链路上。

### 给外行的解释

> "用户发一条消息，不是简单地'服务器转发给对方'。服务器要做的事情有：校验权限 → 消息落库 → 更新每个接收者的会话列表（就是微信首页那个列表，要把这个会话顶到最前面、显示最新一条）→ 把消息实时推给所有在线的接收者。这里面'落库'必须同步做（保证不丢），其余都可以异步做（让发送者尽快得到响应）。**同步和异步的边界怎么切，就是这个系统设计的核心。**"

### 完整链路（对照代码）

```
① 客户端 HTTP POST /capi/chat/msg
        ↓
② ChatServiceImpl.sendMsg()  [@Transactional]
   ├─ check(): 房间成员权限校验（走 RoomCache，不查库）
   ├─ MsgHandlerFactory 按消息类型取策略（文字/图片/语音...）
   ├─ checkAndSaveMsg(): 消息落库
   └─ publishEvent(MessageSendEvent)   ← 只发事件，立刻返回 msgId
        ↓ （事务提交后 AFTER_COMMIT 触发）
③ MessageSendListener 三个监听器并行：
   ├─ pushToOnlineClients(): 直接推送给在线用户（Netty WS）← 保实时
   ├─ messageRoute(): 发 RocketMQ 消息                      ← 保可靠
   └─ handlerMsg(): 触发 AI 回复（如果 @ 了 AI）
        ↓
④ MsgSendConsumer（RocketMQ 消费者）：
   ├─ 更新房间最新消息时间（房间列表排序依据）
   ├─ 更新所有接收者的会话表 contact（写扩散，见 5.3 节）
   └─ 推送消息给房间成员
        ↓
⑤ WebSocketServiceImpl.sendToUid():
   uid → Channel 映射表查在线连接 → 线程池异步 → Netty writeAndFlush
```

关键文件：
- 发送入口：`ChatServiceImpl.java` 的 `sendMsg()`
- 事件监听：`MessageSendListener.java`
- MQ 消费：`MsgSendConsumer.java`
- WS 推送：`WebSocketServiceImpl.java`

### 必须会讲的两个概念

**推拉结合**：发消息用 HTTP（拉模式的基础设施），收消息用 WebSocket（推）。为什么发消息不也走 WebSocket？——HTTP 天然有明确的请求/响应语义，方便做鉴权、限流、重试和错误提示；WebSocket 帧没有内建的"这条请求失败了"语义，全要自己造。业界主流 IM（包括微信网页版）都是这种混合模式。

**写扩散 vs 读扩散** ⭐（群聊设计的核心权衡，5.3 节的优化就建立在这上面）：
- **写扩散**：一条群消息发出时，给群里每个成员的"收件箱"（会话表）各写一条记录。读的时候每人只查自己的收件箱，读很快；但写被放大 N 倍。
- **读扩散**：消息只写一份到房间维度，每个成员读的时候去房间里拉。写只有一次，但读时要聚合计算（未读数、排序），读压力大。
- 本项目当前是**写扩散**（`contactDao.refreshOrCreateActiveTime` 更新全员会话），适合中小群；万人大群（全员群）单独走了**读扩散**（`HotRoomCache`，Redis ZSet 存房间活跃时间，不给每人写会话记录）。**"按房间规模混合使用两种模式"本身就是标准答案**，微信也是类似思路。

## 三、核心设计决策（为什么 → 优点 → 实现）

### 3.1 消息可靠性：本地消息表（SecureInvoke）⭐

**给外行的解释**：
> "发消息有个经典难题：'数据库写入'和'通知 MQ'是两个系统的操作，没法放进同一个事务。如果先写库再发 MQ，MQ 发送失败，后续的会话更新、推送就全丢了；如果先发 MQ 再写库，写库失败，消费者会处理一条不存在的消息。"

**为什么选本地消息表**：分布式事务的常见方案有三种——RocketMQ 事务消息、TCC、本地消息表。事务消息要两阶段回查，实现复杂；TCC 侵入业务；本地消息表最简单：**把"要执行的操作"作为一条记录，和业务数据写进同一个本地事务**，事务要么全成功要么全失败，之后用异步重试保证操作最终执行。

**具体实现**（自研的 `haochat-transaction` 模块，可重点讲这是通用组件设计）：
- 自定义注解 `@SecureInvoke`，AOP 切面 `SecureInvokeAspect` 拦截。
- 如果当前**在事务中**：把方法名、参数序列化成一条记录写入 `secure_invoke_record` 表（与业务同库同事务）；事务提交后异步执行真正的方法调用，成功则删记录。
- 失败自动重试，默认最多 3 次（`maxRetryTimes`），有兜底定时任务扫表补偿。
- `MQProducer.sendSecureMsg()` 就是加了这个注解的可靠发送入口。

**优点**：不引入额外中间件、对业务代码零侵入（一个注解）、和本地事务天然一致。
**缺点（主动说，加分）**：只保证"最终执行"，不保证实时；记录表需要清理；方法参数必须可序列化。

### 3.2 事务事件的时序陷阱：AFTER_COMMIT ⭐

**面试故事线**：`MessageSendListener.java:81` 有一段注释记录了真实踩坑——

> "消息发出后要通知消费者，最初用 Spring 的事务事件在 BEFORE_COMMIT 阶段发 MQ。结果偶发'消费者查不到这条消息'：因为 MQ 消费太快了，消费者拿着 msgId 去查数据库时，**发送方的本地事务还没提交**，按照隔离性根本读不到这行数据。改成 AFTER_COMMIT（事务真正提交后再发 MQ）就解决了。"

这个故事覆盖了三个知识点：Spring 事务事件机制、事务隔离性、分布式系统的时序竞态。一分钟讲完，含金量很高。

追问"如果 AFTER_COMMIT 阶段进程挂了怎么办？"——答：所以 MQ 发送走 `@SecureInvoke` 本地消息表兜底（见 3.1），记录和业务在同一事务里，进程重启后补偿任务会重发。**两个机制是配套的。**

### 3.3 策略模式 + 工厂：多消息类型处理

- 文字/图片/文件/语音/视频/表情/系统消息各一个 Handler，都继承 `AbstractMsgHandler`（模板方法：校验 → 落库 → 构造展示对象）。
- `MsgHandlerFactory` 按消息类型枚举取策略。新增消息类型只加一个类，不改老代码（开闭原则）。
- 消息点赞/点踩同样是策略模式（`AbstractMsgMarkStrategy`）。

### 3.4 缓存体系：旁路缓存 + 批量组装

**为什么**：聊天系统读写比极高（一条消息写一次，被 N 个人读），房间信息、群成员列表、用户信息这类"读多改少"的数据必须挡在 Redis 前面。

**实现**：
- `RoomCache` / `GroupMemberCache` / `UserCache` / `RoomFriendCache`：标准 Cache-Aside（先读缓存，未命中回源 DB 并回填；数据变更时删缓存）。
- **批量组装消除 N+1** ⭐：拉取一页消息时，不是每条消息单独查点赞/用户信息，而是 `getMsgRespBatch()` 把整页消息的 ID 收集起来**一次批量查询** `messageMarkDao.getValidMarkByMsgIdBatch(...)`，再在内存里组装（`ChatServiceImpl.java:357`）。一页 20 条消息，从 20+ 次查询降到 2 次。
- **游标分页替代 offset 分页** ⭐：消息历史用 `CursorPageBaseReq`（游标 = 上一页最后一条的 msgId，`WHERE id < cursor ORDER BY id DESC LIMIT n`）。为什么不用 `LIMIT 100000, 20`？——offset 分页 MySQL 要扫描并丢弃前 10 万行，越翻越慢；游标分页走主键索引直接定位，**深分页耗时恒定**。聊天记录是无限下拉场景，必须用游标。

### 3.5 线程池隔离：三个池子三种语义 ⭐

**给外行的解释**：
> "不同任务的重要性不一样，不能共用一个线程池——不然一类任务堆积会把另一类饿死。更关键的是**队列满了怎么办（拒绝策略）要按业务语义选**。"

`ThreadPoolConfig.java` 三个池子：

| 池子 | 核心/最大/队列 | 拒绝策略 | 为什么 |
|---|---|---|---|
| haochatExecutor（通用异步） | 4/6/200 | **CallerRunsPolicy** | 这些是重要任务（本地消息表补偿等），满了让提交线程自己执行——天然的背压，宁可慢不可丢 |
| websocketExecutor（WS 推送） | 4/8/1000 | **DiscardPolicy** | 推送丢了客户端还能通过拉取兜底，可以丢；不能让推送堆积拖垮主流程 |
| aichatExecutor（AI 回复） | 2/4/15 | DiscardPolicy | AI 回复是增值功能，过载时直接放弃 |

**调优故事**：这几个池子原本按多核大流量配置（10/16/10 常驻线程）。在 2 核容器上，线程数远超核数不提升吞吐，只增加上下文切换和线程栈内存（每线程约 1MB）。按"IO 密集但机器小"的实际情况收紧到上表数值。**"线程池参数要按部署机型定，不是抄公式"**是这个话题的点睛句。

## 四、生产环境实战调优（面试杀手锏）⭐⭐

这一节是真实发生在生产服务器上的排查，是最能和背八股的候选人拉开差距的部分。

### 4.1 RocketMQ Broker 在容器里"假死"的排查 ⭐⭐⭐

**现象**：生产环境群聊消息一直不实时，排查发现所有房间的"最新消息时间"从未更新过——意味着 MQ 消费者从来没消费成功过。但 Broker 进程活着，日志也没有崩溃。

**排查过程**（按这个顺序讲，展示排查方法论）：

1. 查消费位点：`ConsumerOffset` 永远是 0 —— 消息进了 Broker，但从来没被拉走过。
2. 翻 Broker 的 `remoting.log`：每次处理拉取请求都抛 `NoClassDefFoundError: Could not initialize class org.apache.rocketmq.store.StoreUtil`。
3. **关键认知**：`NoClassDefFoundError: Could not initialize class` 不是"类找不到"，而是**这个类的静态初始化曾经失败过一次**。Java 语义：类初始化失败后，这个类在整个 JVM 生命周期内都不可用，后续每次使用都报这个错。
4. 往前翻日志找第一次失败：静态初始化里调用了 JDK 的容器资源探测 API（`Container.metrics()`），它在这台机器的 **cgroup v2** 目录布局下抛了 NPE——JDK 的探测代码没兼容这种布局。
5. **修复**：JVM 参数加 `-XX:-UseContainerSupport` 关掉容器探测。因为堆大小已经用 `-Xms/-Xmx` 显式指定了，根本不依赖 JVM 的自动探测，关掉只是绕开这段有 bug 的代码，无副作用。

**这个故事的知识点密度**：Java 类加载机制（初始化失败的永久性）、JVM 容器感知（UseContainerSupport / cgroup v1 vs v2）、MQ 消费位点排查、"进程活着不代表服务正常"的监控意识。

**修复期间的降级方案**：Broker 修好前，推送链路临时改为**事务提交后直接推送在线用户**（`pushToOnlineClients`），保证用户体验不受排查进度影响——"先止血，再治病"。

### 4.2 容器化 JVM 内存调优

**问题**：整机只有 4G，要塞下 MySQL、Redis、MinIO、RocketMQ×2、后端、前端 7 个容器。任何一个容器内存失控，就会触发 cgroup OOM Kill 连环炸。

**做法与理由**：
- **每个容器都设 memory limit**（Compose `deploy.resources.limits`），且 JVM 堆用 `-Xms/-Xmx` 显式封顶——不能信任 JVM 按宿主机内存自动算堆（RocketMQ 启动脚本曾自动算出 `-Xmx952m`，负载一高 RSS 顶穿容器限制被 OOM 杀）。
- **关 `AlwaysPreTouch`**：RocketMQ 镜像默认开启，它会在启动时把整个堆预先 touch 一遍，导致 RSS 一启动就顶到限制附近，没有任何缓冲余量。
- **JVM 堆 ≠ 容器内存**：堆之外还有元空间、线程栈、直接内存（Netty/RocketMQ 大量使用）、代码缓存。所以 broker 还显式设了 `-XX:MaxDirectMemorySize=128m`，容器限制 = 堆上限 + 直接内存 + ~150M 余量。
- MySQL 同理：`innodb-buffer-pool-size` 按机型显式设置（4G 机型 256M），关 `performance-schema` 省内存。

### 4.3 MQ 消费者线程收紧

RocketMQ 消费者默认 `consumeThreadNumber=20 / consumeThreadMax=64`——是给多核大流量准备的。本项目 4 个消费者 × 默认值 = 上百条常驻线程，在 2 核机器上纯属浪费。显式收紧到 2/4（`MsgSendConsumer.java:43`）。配合 4.2 的线程栈内存分析讲，效果更好。

## 五、性能优化计划（进行中的工作）⭐

> 面试话术："系统跑起来之后我做了一轮系统性的性能审查，找到了几个真实瓶颈，按'先测量、再优化、每步用压测验证'推进。"——**"测量先行"这个方法论本身就是面试加分项。**
>
> **实施状态（2026-07-08）**：5.1 / 5.2 / 5.4 / 5.5（阶段1）与 5.3（阶段2，写扩散去抖）均已在 `perf/optimization` 分支落地并**通过压测验证**。实测数据见下表，可以在面试中引用。
>
> **压测结果（本机 Docker，200 人群，发送约 30 条/秒 + 拉取约 100 次/秒，3.5 分钟混合负载，k6，三轮同负载 A/B/C）**：
>
> | 指标 | 基线 | 阶段1 | 阶段2 | 累计变化 |
> |---|---|---|---|---|
> | 后端 CPU 均值 | 108% | 38% | 36% | **↓ 67%** |
> | MySQL CPU 均值 | 21% | 17% | 11% | **↓ 48%** |
> | 发送延迟均值 | 363ms | 269ms | 151ms | ↓ 58% |
> | 发送延迟 P90 | 1.49s | 836ms | 555ms | ↓ 63% |
> | 发送延迟 P95 | 1.73s | 1.18s | 955ms | ↓ 45% |
> | 读取延迟均值 | 114ms | 120ms | 66ms | ↓ 42% |
> | 读取延迟 P95 | 810ms | 795ms | **105ms** | **↓ 87%** |
> | k6 阈值 | 未达标 | 通过 | 通过 | |
>
> 归因（面试时按这个讲）：阶段1 的 CPU 大降来自 5.5（双重推送摘除）与 5.2（热点房间缓存不再每条消息回源）；阶段2 的 MySQL 负载减半与读取 P95 暴跌来自 5.3（contact 写扩散去抖——数据库不再被每秒 30×200 行的 upsert 挤占，读查询不用再排队）。发送失败均为频控业务拒绝（三轮条件相同）。一致性校验：压测结束后全员 contact.last_msg_id 与最新消息完全一致，运行期零异常、零合并刷新失败。

> 测量口径要诚实：单轮测试、开发机 Docker 环境，数字是**方向性**的；上服务器后建议低峰期复测。后一轮均跑在更大数据集上（累计 1.3 万+消息），偏差方向对结论保守。

### 5.0 为什么先建基准（阶段 0）

- 用 k6 写了压测脚本（`perf/` 目录）：模拟多虚拟用户持续发消息/拉消息，阶梯加压（5→10→20 VU），断言 P95 < 1.5s、错误率 < 2%。
- 开 MySQL 慢查询日志（`long_query_time=0.2`）、Spring Boot Actuator 暴露 JVM/线程池指标。
- **为什么必须先做**：没有基线，优化后说"变快了"没有说服力；而且直觉找的瓶颈经常是错的，数据会指出真正的热点。

### 5.1 WS 推送的重复序列化（低成本高收益）✅已实现，已验证

**问题**：`WebSocketServiceImpl.java:300`，推送时**每个 channel 都执行一次 JSON 序列化**：
```java
channel.writeAndFlush(new TextWebSocketFrame(JSONUtil.toJsonStr(wsBaseResp)));
```
全员广播给 1000 个在线用户 = 同一条消息序列化 1000 次。序列化是 CPU 密集操作，这是纯浪费。

**方案**：在 `sendToAllOnline` / `sendToUid` 入口处**序列化一次**，把 JSON 字符串传下去；进一步可以共享 Netty 的 `ByteBuf`（`retainedDuplicate()`）连内存拷贝都省掉。

**面试引申**：这是"广播场景下把循环不变量提出循环"的典型案例；同类思路在 Kafka 的零拷贝、Netty 的 ByteBuf 引用计数里都有体现。

### 5.2 每条消息击穿房间缓存 ✅已实现，已验证

**问题**：`MsgSendConsumer.java:92`，每条消息处理完都 `roomCache.delete(roomId)`。后果：**消息越活跃的房间，缓存命中率越低**——刚删完，下一条消息的权限校验又要回源 MySQL，接着又删。热门房间等于没有缓存。

**为什么原来这么写**：Cache-Aside 的标准做法是"改数据删缓存"，防止缓存与 DB 不一致。但这里变更的只有 `activeTime` 一个字段，且对一致性不敏感（差几百毫秒无感知）。

**方案**：改为**原地更新缓存**中的 activeTime 字段，或对删除做合并窗口（同房间 X 秒内只删一次）。

**面试引申**：Cache-Aside "删除优于更新"是通用原则，但**原则要看数据特性**——对高频写、弱一致性要求的字段，教条式删除反而制造了缓存击穿。能讲出"什么时候可以违反最佳实践"比背诵最佳实践更有说服力。

### 5.3 群聊写扩散的写放大（最核心的优化）⭐⭐ ✅已实现，已验证

**问题**：`MsgSendConsumer.java:108`——每条群消息都对**全体群成员**执行会话表 upsert：
```java
contactDao.refreshOrCreateActiveTime(roomId, memberUidList, msgId, createTime);
```
500 人群每条消息 = 500 行写。如果群里每秒 10 条消息，就是每秒 5000 行 upsert，MySQL 先扛不住。**这是系统规模化的头号瓶颈。**

**方案对比**（面试时把三个方案都摆出来，展示决策过程）：

| 方案 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| a. 大群转读扩散 | 大群不写成员会话表，读会话列表时用房间的 last_msg_id 实时算 | 彻底消除写放大 | 会话列表查询变复杂，未读数要另想办法（Redis 计数） |
| b. 合并窗口去抖 | 同房间 X 秒内的多条消息，只触发一次全员会话刷新 | 改动小，收益立竿见影（高频房间写量降一个数量级） | 会话列表的"最新消息"有 X 秒延迟 |
| c. SQL 批量优化 | 逐行 upsert 改单条批量语句 | 无语义变化 | 只降低常数，不改变 O(N) 本质 |

**推荐路径**：先 c（无风险）+ b（去抖窗口 1~2 秒，用户无感知），压测验证；成员数超过阈值（如 1000 人）的群自动切 a 模式——**这正是项目里全员群（HotRoom）已经在用的模式，等于把已验证的设计推广到大群**。

**实际落地（2026-07-08）**：审查发现 c 已存在（mapper 是单条批量 `INSERT ... ON DUPLICATE KEY UPDATE`，且用 `GREATEST` 保证并发消费乱序时 last_msg_id 只前进不后退——这个细节本身值得讲）。因此实现了 b：新增 `ContactRefreshBuffer`（`ConcurrentHashMap` 按房间合并 + `@Scheduled` 每秒冲刷），`MsgSendConsumer` 提交合并请求而非直接刷库。**合并的正确性依据**：刷新 SQL 的 GREATEST 单调语义使"取窗口内最大 msgId 刷一次"与"逐条刷 N 次"结果完全等价（幂等+单调），这是可以去抖的前提。主动讲代价：会话列表最多延迟 1 秒；进程崩溃丢窗口内合并记录但下一条消息自愈；仅适用单实例，多实例要按 roomId 分片或落 Redis。实测：MySQL CPU 17%→11%，读取 P95 795ms→105ms（写不再挤占读），发送 P95 1.18s→955ms。

**必背知识点**：微信按此思路设计——普通群写扩散，直播间/大群读扩散。"没有银弹，按房间规模混合"是标准答案。

### 5.4 静默丢消息的可观测性 ✅已实现，已验证

**问题**：WS 推送线程池用 `DiscardPolicy`，队列满时任务被**无声无息**丢掉——没有日志、没有计数。用户表现为"偶尔收不到消息"，且无法排查。

**方案**：自定义拒绝处理器：丢弃时递增计数指标 + 采样日志。有了数据才能回答"要不要扩队列/换策略"。**"先让丢弃可见，再决定要不要消灭丢弃"**——可观测性先于优化。

### 5.5 双重推送问题（审查代码时新发现）⭐ ✅已实现，已验证

**发现过程**：梳理链路时发现同一条消息被推送**两次**——`MessageSendListener.pushToOnlineClients()`（事务提交后直推）和 `MsgSendConsumer.onMessage()`（MQ 消费后又推了一次）。

**根因是演进遗留**：Broker 假死期间（见 4.1）加了直推作为止血方案；后来 Broker 修好了，消费路径的推送恢复工作，但直推没有摘除——每条消息推两遍，推送负载翻倍。客户端按消息 ID 去重了所以用户无感，但服务端在做双倍的无用功。

**修复**：消费者只保留会话更新等数据类任务，推送职责统一归直推路径。

**面试价值**：这是"止血方案变成永久方案"的经典技术债案例。讲它展示两点——你会主动做链路审查，以及你理解"临时方案要带着摘除计划"。

### 5.6 移除 RocketMQ 的架构权衡（单实例场景）

**思考**："这个架构里 MQ 到底在换取什么？"MQ 的三大价值——解耦、削峰、跨实例广播。当前**单实例**部署下：解耦用 Spring 事件也能做到；削峰有限（消费者就在同一进程隔壁）；跨实例广播用不上。而成本是实打实的：namesrv + broker 两个容器约 900MB 内存限额 + 每条消息多一跳网络。

**方案**：消费者逻辑改为进程内异步事件（可靠性由本地消息表继续兜底），省出的内存转给 MySQL buffer pool（256M→512M+）和后端堆。

**必须主动说的反面**：如果未来要多实例横向扩展，MQ 就必须加回来——因为 WebSocket 连接分散在不同实例上，消息必须广播给所有实例才能找到接收者的连接。**"架构决策要匹配当前规模，并给未来留好回退路径"**是这个话题的落点。

### 5.7 前端加载优化

- **已有**：虚拟滚动（万条消息只渲染可视区）、Element Plus 按需引入、路由分包、gzip 预压缩、图片压缩。
- **计划**：
  - Caddy 对带内容 hash 的静态资源加 `Cache-Control: max-age=31536000, immutable`（文件名含 hash，内容变则名变，可以永久缓存）；`index.html` 加 `no-cache`（每次协商，保证发版即生效）。**这一对配置是 SPA 缓存策略的标准答案。**
  - gzip 之外增加 brotli 预压缩（同等级别体积再小 15~20%）。

## 六、高频追问 Q&A

**Q1：你的压测怎么做的？关注什么指标？**
> k6 脚本模拟真实行为（登录拿 token → 循环发消息/拉历史），阶梯加压观察拐点。核心指标：P95/P99 延迟（比平均值更能反映用户体验）、错误率、以及服务端的 CPU/内存/GC 频率/慢查询数。先压出基线，每做一项优化重新压一轮对比，用数据说话。

**Q2：消息不丢是怎么保证的？**
> 分层保证：① 发送阶段——HTTP 同步落库成功才返回，客户端失败可重试；② 异步任务阶段——本地消息表（@SecureInvoke）与业务同事务落库，失败自动重试；③ 推送阶段——推送本身允许丢（在线推送只是加速），客户端拉取消息历史是最终兜底。**"推送保实时、拉取保可靠"**。

**Q3：消息顺序怎么保证？**
> 存储顺序由数据库自增 msgId 天然保证，客户端按 msgId 排序渲染。推送乱序不影响最终一致。特例是 AI 流式回复：同一条回复的片段必须按序到达，所以走 `sendToUidSync`（不进线程池、调用线程直接顺序写出）——**通用路径用池化换吞吐，保序路径用同步换顺序**，按需选择。

**Q4：WebSocket 连接是怎么管理的？**
> Netty 单独起在 8090 端口。两张内存表：`Channel → 用户信息` 和 `uid → Channel 列表`（一个用户多端登录对应多个连接）。上线时注册、断线时清理并广播下线事件。心跳用 Netty 的 IdleStateHandler 空闲检测踢掉死连接。

**Q5：如果要支持多实例部署，怎么改？**
> 核心问题是连接分散：用户 A 连在实例 1，给他发消息的请求可能落在实例 2。两种做法：① MQ 广播模式，所有实例都消费，各自检查目标用户是否连在本机（简单，但有无效消费）；② 用 Redis 维护 uid→实例 的路由表，定向投递（精确，但要处理路由表一致性）。中小规模选 ①，这也是为什么说单实例阶段撤掉的 RocketMQ 到时候要加回来。

**Q6：Redis 挂了系统会怎样？**
> 缓存类数据（房间/群成员/用户）回源 MySQL，性能下降但功能可用；在线状态和热门群聊 ZSet 会丢，用户重连后自动重建。属于"降级可用"设计。

**Q7：为什么用 Netty 而不是 Spring 自带的 WebSocket？**
> Spring WebSocket（基于 Tomcat）一个连接的处理模型更重；Netty 的事件循环模型单机可以扛更多长连接，且对 ByteBuf、心跳、编解码的控制粒度更细。IM 场景连接数是核心指标，值得为此引入 Netty。

**Q8：数据库层面做了什么优化？**
> 游标分页（消息历史）、批量查询消除 N+1（消息标记）、buffer pool 按机型调整、慢查询日志驱动索引审查（消息表 (room_id, id) 联合索引覆盖游标查询，会话表 (room_id, uid) 唯一索引支撑 upsert）。

**Q9（如果被问到数字）：优化效果如何？**
> ⚠️ 压测跑完前不要编数字。可以说："基线压测在 20 并发用户下发送 P95 约 X ms；序列化优化和写扩散去抖上线后计划复测，我预期推送 CPU 占用和 MySQL 写 QPS 都有数量级级别的改善。" —— **压测完成后回来把真实数字填进这里。**
