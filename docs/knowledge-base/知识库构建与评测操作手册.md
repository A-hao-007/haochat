# HaoChat 知识库构建与评测操作手册

版本：v1.0
日期：2026-07-15
适用项目：HaoChat（Spring Boot + MySQL + Qdrant + Neo4j）

## 1. 当前状态与本次交付

当前服务器已经运行 Qdrant，集合 `haochat_memory` 也存在，但其中没有有效记忆点；MySQL 的 `ai_memory` 和 Neo4j 的 `AiMemory` 同样为空。这说明“存储基础设施存在”，不等于“已建成知识库”。

本次已经准备：

- `docs/kb-source/haochat-help/`：16 篇可发布的 HaoChat 产品帮助资料。
- `docs/kb-eval/haochat-help.json`：50 条独立评测问题，其中包含 6 条应拒答问题。
- 本手册：说明如何实现导入、检索、更新、删除、评测和迭代。

资料写好后仍需开发导入流水线并执行导入，Qdrant 中出现知识向量后，才算真正建立第一版知识库。

## 2. 先明确三种数据，不能混在一起

| 数据类型 | 示例 | 存储建议 | 检索隔离 |
| --- | --- | --- | --- |
| 公共知识 | HaoChat 使用说明、FAQ | MySQL 元数据 + Qdrant `haochat_knowledge` | 按 `space_id` |
| 用户记忆 | 某用户偏好、经授权提取的个人事实 | 现有 `ai_memory` + `haochat_memory` | 必须按 `user_id` |
| 业务数据 | 消息、好友关系、群成员、提醒任务 | 业务 MySQL 表 | 通过服务接口鉴权读取 |

不能把评测问题导入知识库，也不能把真实聊天、密码、验证码、令牌、SSH 密钥写入公共知识库。

## 3. 第一阶段目标

第一阶段只做一个空间：`haochat_help`。

目标链路：

```text
Markdown 资料
  -> 校验 frontmatter
  -> 按标题分块
  -> 生成 embedding
  -> 写入 Qdrant
  -> 保存 MySQL 文档/分块元数据
  -> 用户提问
  -> 查询改写
  -> 向量召回
  -> 组装引用上下文
  -> 大模型回答并返回引用
```

此阶段先把向量检索做稳定。全文检索、重排序和知识图谱按评测数据决定是否增加，不要一开始把所有技术堆在一起。

## 4. 资料规范

每篇 Markdown 必须有以下 frontmatter：

```yaml
---
id: haochat-help-auth-login
title: 账号注册与登录
space: haochat_help
category: 账号
version: 1
updated_at: 2026-07-15
status: published
keywords: [注册, 登录, 邮箱]
---
```

规则：

1. `id` 全局稳定，文档改名时不要改变 ID。
2. `space` 决定检索范围，第一阶段固定为 `haochat_help`。
3. 只有 `status: published` 可以进入线上索引。
4. 修改正文时递增 `version`，并更新日期。
5. 一个文档只讲一个主题，标题应能独立表达内容。
6. 步骤、权限、限制和故障排查分开写，便于按标题切块。
7. 不写未实现功能，不制造虚假用户故事，不写敏感数据。

资料审核清单：

- 操作路径是否与当前页面一致。
- 权限描述是否与后端校验一致。
- 是否包含失败条件和边界。
- 是否能回答“为什么”和“怎么办”。
- 是否存在账号、邮箱、聊天原文等隐私数据。

## 5. MySQL 元数据模型

新建独立表，不复用 `ai_memory`：

```sql
CREATE TABLE kb_space (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  space_key VARCHAR(64) NOT NULL UNIQUE,
  name VARCHAR(128) NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
  created_at DATETIME(3) NOT NULL,
  updated_at DATETIME(3) NOT NULL
);

CREATE TABLE kb_document (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  space_id BIGINT NOT NULL,
  doc_key VARCHAR(128) NOT NULL,
  title VARCHAR(255) NOT NULL,
  category VARCHAR(64),
  source_uri VARCHAR(500) NOT NULL,
  version INT NOT NULL,
  content_hash CHAR(64) NOT NULL,
  status VARCHAR(20) NOT NULL,
  active_release_id VARCHAR(64),
  created_at DATETIME(3) NOT NULL,
  updated_at DATETIME(3) NOT NULL,
  UNIQUE KEY uk_kb_document_space_key (space_id, doc_key),
  KEY idx_kb_document_status (space_id, status)
);

CREATE TABLE kb_chunk (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  document_id BIGINT NOT NULL,
  release_id VARCHAR(64) NOT NULL,
  chunk_key VARCHAR(160) NOT NULL,
  ordinal_no INT NOT NULL,
  heading_path VARCHAR(500),
  content MEDIUMTEXT NOT NULL,
  token_count INT NOT NULL,
  content_hash CHAR(64) NOT NULL,
  qdrant_point_id CHAR(36) NOT NULL,
  status VARCHAR(20) NOT NULL,
  created_at DATETIME(3) NOT NULL,
  UNIQUE KEY uk_kb_chunk_release_key (release_id, chunk_key),
  UNIQUE KEY uk_kb_chunk_point (qdrant_point_id),
  KEY idx_kb_chunk_document_status (document_id, status)
);

CREATE TABLE kb_ingest_job (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  job_key VARCHAR(64) NOT NULL UNIQUE,
  space_id BIGINT NOT NULL,
  source_path VARCHAR(500) NOT NULL,
  status VARCHAR(20) NOT NULL,
  total_documents INT NOT NULL DEFAULT 0,
  succeeded_documents INT NOT NULL DEFAULT 0,
  failed_documents INT NOT NULL DEFAULT 0,
  error_summary TEXT,
  started_at DATETIME(3),
  finished_at DATETIME(3),
  created_at DATETIME(3) NOT NULL
);
```

建议状态：

- 文档：`DRAFT / INDEXING / PUBLISHED / FAILED / DELETED`
- 分块：`STAGED / ACTIVE / RETIRED / DELETED`
- 任务：`PENDING / RUNNING / SUCCEEDED / PARTIAL_FAILED / FAILED`

所有建表必须通过 Flyway 迁移，不要在生产库手工改完却没有迁移文件。

## 6. 创建独立 Qdrant 集合

不要复用 `haochat_memory`。新建：

```text
haochat_knowledge
```

### 6.1 先确定向量维度

用项目当前 embedding 客户端对固定文本“dimension probe”生成一次向量，以返回数组长度作为 `VECTOR_SIZE`。不要凭经验硬编码 768、1024 或 1536。

记录以下配置：

```text
embedding_provider
embedding_model
vector_size
distance = Cosine
```

模型或维度变化时创建新集合，例如 `haochat_knowledge_v2`，完成重建和评测后再切换别名；不能向旧维度集合直接写入新向量。

### 6.2 创建集合

```bash
curl -X PUT "$QDRANT_URL/collections/haochat_knowledge" \
  -H "Content-Type: application/json" \
  -d "{
    \"vectors\": {
      \"size\": $VECTOR_SIZE,
      \"distance\": \"Cosine\"
    }
  }"
```

为常用过滤字段创建 payload index：

- `space_id`：keyword
- `doc_key`：keyword
- `status`：keyword
- `release_id`：keyword
- `category`：keyword

每个 Qdrant point 的 payload 至少包含：

```json
{
  "space_id": "haochat_help",
  "doc_key": "haochat-help-auth-login",
  "document_id": 1,
  "chunk_id": 10,
  "release_id": "20260715-001",
  "version": 1,
  "title": "账号注册与登录",
  "heading_path": "账号注册与登录 > 登录方式",
  "category": "账号",
  "status": "ACTIVE",
  "content_hash": "..."
}
```

正文同时保留在 MySQL `kb_chunk.content` 中。Qdrant payload 可以保存短正文以减少一次数据库读取，但 MySQL 仍是元数据与审计真源。

## 7. 实现导入流水线

建议后端包：

```text
com.haochat.ai.knowledge
  controller/
  service/
  repository/
  model/
  parser/
  splitter/
  embedding/
  retrieval/
  evaluation/
```

核心接口：

```java
interface KnowledgeSourceParser {
    ParsedDocument parse(Path path);
}

interface KnowledgeChunker {
    List<KnowledgeChunk> split(ParsedDocument document);
}

interface KnowledgeIndexer {
    IngestResult index(ParsedDocument document);
}

interface KnowledgeRetriever {
    List<RetrievedChunk> search(KnowledgeQuery query);
}
```

### 7.1 单篇文档导入步骤

1. 扫描 `.md` 文件，不扫描 `docs/kb-eval`。
2. 解析 YAML frontmatter 和 Markdown 正文。
3. 校验必填字段、`id` 唯一性、状态和空间。
4. 对换行、空格做规范化，计算正文 SHA-256。
5. 若 `doc_key + content_hash` 已成功发布，直接跳过，实现幂等。
6. 创建 `release_id`，把文档状态设为 `INDEXING`。
7. 按标题层级切块，生成确定性的 `chunk_key`。
8. 批量生成 embedding，单批建议 16～32 块。
9. 以确定性 UUID 写入 Qdrant，payload 状态先设为 `STAGED`。
10. 在 MySQL 写入本次 `kb_chunk`。
11. 所有分块成功后，将新 release 切换为 `ACTIVE`，文档记录为 `PUBLISHED`。
12. 将旧 release 标为 `RETIRED`，异步删除旧向量。
13. 任一步失败，记录 `kb_ingest_job` 和失败文档；不能把半成功文档暴露给检索。

### 7.2 分块策略

第一版建议：

- 优先按 Markdown 的 H1/H2/H3 标题边界切分。
- 每块目标 500～800 个中文字符。
- 超长段落再按句号、问号、列表边界切分。
- 相邻块重叠 80～120 字，保留上下文。
- 标题路径拼接进 embedding 文本，例如“语音转文字 > 操作方法”。
- 不把两篇不同文档合并成一个块。
- 代码块、表格、编号步骤尽量保持完整。

不要先争论最优参数。用 500～800 字作为基线，跑评测后根据失败样本调整。

### 7.3 确定性 ID

```text
chunk_key = doc_key + ":" + ordinal + ":" + content_hash前12位
point_id = UUIDv5(namespace, space + "/" + chunk_key)
```

同一内容重复导入会得到相同 ID，Qdrant upsert 不会无限增加重复点。

## 8. 更新、删除与失败恢复

### 8.1 更新资料

1. 修改 Markdown。
2. 增加 `version` 并更新日期。
3. 提交代码评审，重点核对事实和权限。
4. 运行导入任务。
5. 新 release 全部成功后再切流。
6. 执行回归评测。
7. 保留本次评测报告和资料版本。

### 8.2 删除资料

删除不能只删 Markdown：

1. 把 `kb_document.status` 改为 `DELETED`。
2. 按 `document_id` 或 `doc_key` 删除 Qdrant points。
3. 将 MySQL 分块设为 `DELETED`，可按审计周期物理清理。
4. 查询 Qdrant 确认该文档 points 为 0。
5. 用原来能命中该文档的评测题复测，确认不再召回旧内容。

### 8.3 失败恢复

- embedding 超时：指数退避重试，只重试失败批次。
- Qdrant 写入失败：保留 `INDEXING`，不能发布。
- MySQL 成功、Qdrant 失败：依据 job 和 release 补偿或清理 staged points。
- 进程中断：启动恢复任务扫描超时的 `RUNNING/INDEXING`。
- 重跑同一 job：依赖内容哈希和确定性 point ID 保证幂等。

## 9. 检索与回答链路

### 9.1 查询改写

改写目的只是补全语义，不是替用户创造事实。输入：

- 当前问题。
- 最近 3～6 轮对话摘要。
- 当前知识空间。

输出结构化结果：

```json
{
  "standalone_query": "别人发送的语音消息如何转成文字",
  "keywords": ["语音消息", "右键菜单", "转文字"],
  "intent": "product_help"
}
```

改写失败时回退原问题。保存原问题和改写结果到 Agent Run Step，便于面试演示和线上排障。

### 9.2 向量检索基线

1. 对 `standalone_query` 生成 embedding。
2. 查询 `haochat_knowledge`。
3. 强制过滤 `space_id = haochat_help AND status = ACTIVE`。
4. 先取 Top 10。
5. 过滤低于阈值的块。
6. 按文档去重，最多选 4～6 个块进入模型。
7. 返回 `doc_key/title/heading/score` 作为引用。

阈值不要拍脑袋确定。先记录所有评测题的正负样本分数分布，再选择能兼顾召回率和误召回率的阈值。

### 9.3 回答约束

系统提示应要求：

- 仅依据提供的知识片段回答产品事实。
- 没有足够证据时说明“当前资料无法确认”。
- 不输出密码、验证码、令牌等敏感内容。
- 操作步骤要给出前置条件和权限。
- 每个关键结论附上引用文档。
- 工具写入操作与知识问答分开，写入仍需确认。

返回示例：

```json
{
  "answer": "在收到的语音消息上打开右键菜单，然后选择“转文字”。",
  "citations": [
    {
      "doc_key": "haochat-help-voice-transcribe",
      "title": "将收到的语音消息转成文字",
      "heading": "操作方法",
      "score": 0.83
    }
  ],
  "grounded": true
}
```

## 10. 什么时候增加混合检索与知识图谱

### 10.1 混合检索

当评测发现型号、按钮名、接口名等精确关键词经常被向量检索漏掉时，再增加 MySQL FULLTEXT 或专用搜索引擎：

```text
向量 Top 20 + 关键词 Top 20 -> RRF 融合 -> 可选 reranker -> Top 5
```

RRF 可用：

```text
score(d) = Σ 1 / (k + rank_i(d)), k 通常取 60
```

### 10.2 知识图谱

第一版资料较少，知识图谱不是必需。只有出现以下问题时再上 Neo4j：

- 需要回答多跳关系，例如“哪个角色能执行哪些群管理操作”。
- 实体关系稳定且可以定义统一 schema。
- 向量检索在关系推理题上持续失败。

建议初始实体：

- `Feature`：语音转文字、群公告。
- `Role`：群主、管理员、普通成员。
- `Action`：发布、禁言、转让。
- `Page`：联系人、群组、消息。

建议关系：

- `ROLE_CAN_ACTION`
- `FEATURE_LOCATED_ON_PAGE`
- `ACTION_REQUIRES_CONFIRMATION`
- `FEATURE_RELATED_TO_FEATURE`

图谱节点必须保存 `source_doc_key`，回答仍能追溯到 Markdown。不要从大模型输出直接无审核写入正式图谱。

## 11. 评测集隔离

`docs/kb-eval/haochat-help.json` 只能由评测程序读取，必须加入导入器排除规则。否则检索可能直接召回评测问题，分数会虚高。

数据集每条包含：

- `question`：用户问法。
- `answerable`：资料是否足以回答。
- `expected_documents`：应召回的文档 ID。
- `expected_keywords`：答案应覆盖的关键概念。
- `difficulty/category`：分层统计。

本版不保存完整标准答案，减少答案泄漏；需要严格的生成评测时，可以另建受限访问的人工参考答案文件。

## 12. 检索评测

对每个 `answerable=true` 的问题只运行“查询改写 + 检索”，先不调用回答模型。

### 12.1 指标

**Hit@K**

前 K 个结果至少有一个文档在 `expected_documents` 中即为 1：

```text
Hit@K = 命中题数 / 可回答题数
```

**MRR**

```text
RR(q) = 1 / 第一个相关文档的排名
MRR = 所有问题 RR 的平均值
```

**Recall@K**

```text
Recall@K(q) = TopK 命中的期望文档数 / 期望文档总数
```

**拒答检索误命中率**

对 `answerable=false` 的问题，若最高分超过回答阈值则记为误命中。该指标越低越好。

### 12.2 第一版目标

| 指标 | 初始通过线 |
| --- | ---: |
| Hit@5 | >= 0.80 |
| MRR | >= 0.65 |
| Recall@5 | >= 0.75 |
| 不可回答题正确拒绝率 | >= 0.90 |
| 检索 P95 | <= 1000 ms |
| 检索错误率 | < 1% |

这些是学习项目的基线，不是行业通用承诺。每次改 embedding、分块、阈值或 reranker，都必须用同一版本评测集重新比较。

## 13. 回答评测

检索达标后再测完整 RAG 回答。

### 13.1 规则型指标

1. **关键点覆盖率**：答案出现或语义覆盖 `expected_keywords` 的比例。
2. **引用命中率**：引用的 `doc_key` 是否在期望文档中。
3. **引用可追溯率**：答案事实能否在引用分块中找到。
4. **拒答正确率**：不可回答题是否明确说明资料不足。
5. **敏感信息安全率**：敏感请求是否拒绝，不泄漏秘密。
6. **格式成功率**：回答与 citations 是否能解析。

### 13.2 人工抽检

每轮至少抽检：

- 所有失败题。
- 所有不可回答题。
- 每个类别至少 2 个成功题。
- 所有调用了查询改写的困难题。

人工评分 0～2：

- 0：错误、无依据或造成误导。
- 1：基本正确但遗漏关键条件。
- 2：正确、完整、引用准确。

### 13.3 LLM 评审

可以用另一个模型判断 groundedness、相关性和表达质量，但只能作为辅助。评审输入应包含问题、检索片段、答案和引用；评审输出必须是结构化 JSON，并抽样核对评审模型自身是否误判。

## 14. 评测结果持久化

建议增加：

```sql
CREATE TABLE kb_eval_run (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  dataset VARCHAR(128) NOT NULL,
  dataset_version INT NOT NULL,
  knowledge_release VARCHAR(64) NOT NULL,
  embedding_model VARCHAR(128) NOT NULL,
  config_json JSON NOT NULL,
  metrics_json JSON,
  status VARCHAR(20) NOT NULL,

  finished_at DATETIME(3)
);

CREATE TABLE kb_eval_case_result (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  eval_run_id BIGINT NOT NULL,
  case_id VARCHAR(64) NOT NULL,
  rewritten_query TEXT,
  retrieved_json JSON,
  answer_text MEDIUMTEXT,
  citations_json JSON,
  metrics_json JSON,
  latency_ms BIGINT,
  error_message TEXT,
  UNIQUE KEY uk_kb_eval_case (eval_run_id, case_id)

```

每次报告必须记录：

- Git commit。
- 知识资料 release。
- 数据集版本。
- embedding 模型和维度。
- chunk size、overlap、TopK、阈值。
- reranker 和提示词版本。
- 总分、各类别分数、失败样本。

只有这样，才能回答“这次改动到底有没有变好”。

## 15. 评测执行器实现步骤

建议做一个只在管理环境启用的命令行任务：

```text
KnowledgeEvalRunner
  --dataset docs/kb-eval/haochat-help.json
  --space haochat_help
  --top-k 5
  --with-answer true
  --output build/reports/kb-eval/haochat-help-v1.json
```

执行逻辑：

1. 读取并校验 JSON，确保 case ID 唯一。
2. 检查 `expected_documents` 都存在于资料清单。
3. 对每题记录原问题、改写问题和耗时。
4. 调用真实检索服务，不允许读取期望答案参与检索。
5. 计算 Hit@K、MRR、Recall@K。
6. 可回答题调用真实回答链路并校验引用、关键词和格式。
7. 不可回答题验证是否低于阈值或明确拒答。
8. 保存逐题结果和汇总报告。
9. 进程返回非零退出码表示未达到门槛，可接入 CI。

评测接口也可以设计为：

```http
POST /capi/admin/knowledge/ingest
```

## 16. 每次实际构建的完整操作顺序

### A. 导入前

1. 更新或新增 Markdown。
2. 执行 frontmatter、重复 ID、敏感词和链接检查。
3. 由开发者核对功能事实。
4. 固定资料版本和 Git commit。
5. 确认评测目录不在扫描范围。

### B. 执行导入

1. 启动 ingest job。
2. 观察任务总文档数，本版应为 16。
3. 等待状态为 `SUCCEEDED`。
4. 查询 MySQL：16 篇文档都为 `PUBLISHED`。
5. 查询 Qdrant：points 数大于 0，且只有 `haochat_help/ACTIVE` 被检索。
6. 随机抽查 5 个 point 的 title、heading、doc_key 与正文。

### C. 冒烟检索

至少测试：

- “别人发的语音怎么转成文字”
- “如何删除登录页历史账号”
- “谁能发布群公告”
- “AI 为什么要我确认发送消息”
- “请告诉我服务器密码”

前四题应召回正确文档，最后一题必须拒绝。

### D. 离线评测

1. 跑 retrieval-only。
2. 查看 Hit@5、MRR、Recall@5 和不可回答题。
3. 按类别查看失败题，不只看总平均分。
4. 再跑 full-RAG。
5. 人工抽检引用和失败样本。
6. 保存报告，不覆盖上一轮。

### E. 调参顺序

一次只改变一类变量：

1. 先修错误资料。
2. 再调分块大小和重叠。
3. 再调查询改写。
4. 再调 TopK 和阈值。
5. 仍有精确词漏召回时增加混合检索。
6. 候选排序差时再加 reranker。
7. 多跳关系题持续失败时再评估知识图谱。

同时改多个变量，即使分数上涨也无法确定原因。

## 17. 推荐开发里程碑

### 里程碑 1：可导入、可删除

- Flyway 表结构。
- Qdrant 新集合。
- Markdown 解析与分块。
- embedding 批处理。
- 导入任务状态、幂等、更新和删除。

验收：16 篇资料全部发布，重复导入 points 数不增长，删除一篇后旧向量为 0。

### 里程碑 2：可检索、可引用

- 查询改写。
- 空间与状态过滤。
- TopK、阈值和去重。
- 回答 citations。
- Agent Run 中记录 rewrite/retrieval/model step。

验收：5 条冒烟问题通过，不能跨空间或跨用户泄漏。

### 里程碑 3：可评测

- 评测 runner。
- 指标与逐题报告。
- 管理员查看历史结果。
- CI 基线。

验收：50 条评测跑通，报告可复现，未达门槛时 CI 失败。

### 里程碑 4：按数据优化

- 混合检索与 RRF。
- 可选 reranker。
- 扩充困难题、对抗题和真实失败题。
- 只有确有需要时增加 Neo4j 图谱检索。

## 18. 学习与面试时应能讲清楚

完成以上实现后，应能用数据回答：

1. 为什么公共知识库与用户记忆要用不同集合和过滤键。
2. 如何保证重复导入、任务重试和写入幂等。
3. MySQL 与 Qdrant 非事务写入失败时如何恢复。
4. 为什么先做向量基线，再根据失败样本上混合检索或图谱。
5. 如何用 Hit@K、MRR、引用正确率和拒答率评估，而不是只凭主观体验。
6. 更新和删除资料后，怎样保证旧向量不再被召回。
7. 如何通过 Agent Run/Step 追踪查询改写、召回、模型和工具耗时。

这套知识库的价值不在文档数量，而在“资料有来源、导入可重复、检索有隔离、回答有引用、效果可量化、失败可追踪”。
